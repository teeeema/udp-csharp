## 2. Обмен ключами: X25519 + HKDF-SHA256

Реализовать обмен ключами при установлении UDP-сессии.

Порядок:

1. Клиент создаёт эфемерную пару ключей X25519.
2. Отправляет `KEY_EXCHANGE` с открытым ключом.
3. Сервер создаёт собственную эфемерную пару.
4. Сервер возвращает открытый ключ.
5. Обе стороны вычисляют общий секрет X25519.
6. Через HKDF-SHA256 формируются ключи шифрования сессии.
7. Сессия переходит в состояние ESTABLISHED только после успешного согласования и предусмотренного подтверждения ключей.

Требования:

- Использовать криптографически стойкую случайность.
- Предусмотреть тайм-ауты, повторную отправку сообщений согласования и очистку неуспешных сессий.
- Проверять длины сообщений и корректность открытых ключей.
- Для клиентского и серверного направлений использовать разные криптографические ключи или надёжно разделённые nonce-пространства; предпочтительно разные ключи, производные через HKDF.
- Привязать сессионные ключи к контексту согласования, направлению передачи и идентификатору сессии.
- Не хранить ключи в логах.
- Не использовать один глобальный ключ для всех игроков.
- Не разрешать передачу игровых команд до успешного установления защищённой сессии.

Учесть, что неаутентифицированный X25519 не предотвращает MITM. Не заявлять обратное. Если механизм аутентификации сервера отсутствует, документировать ограничение и предложить совместимый способ усиления, например PSK или подпись ключа.

## 3. Шифрование AES-256-GCM

Реализовать функции, эквивалентные:

- `EncryptAES()`
- `DecryptAES()`

Алгоритм — AES-256-GCM.

Формат согласно методичке:

`[открытый заголовок][nonce 12 байт][ciphertext N байт][tag 16 байт]`

Требования:

- Размер ключа — 32 байта.
- Размер nonce — 12 байт.
- Размер authentication tag — 16 байт.
- Заголовок остаётся открытым, но обязательно включается в AAD.
- После создания тега все поля AAD должны оставаться неизменными.
- Все поля заголовка, включая payloadSize, должны иметь окончательные значения до выполнения шифрования.
- Каждый новый шифруемый пакет получает уникальный nonce в пределах своего ключа.
- Не использовать `rand()` для создания nonce.
- Чётко определить порядок байтов числовых полей.
- При неверном authentication tag пакет отклонять до десериализации и исполнения.
- При криптографической ошибке очищать частично полученный plaintext.
- Проверять размеры, переполнения и границы буферов.

При повторной отправке надёжного пакета разрешается передавать сохранённый исходный зашифрованный datagram, не выполняя новое шифрование с прежним nonce.

Нельзя шифровать новый или изменённый plaintext с уже использованной парой ключ + nonce.

## 4. Интеграция в существующий UDP-протокол

Добавить или адаптировать типы:

- `KEY_EXCHANGE = 10`
- `ENCRYPTED = 11`

Если данные идентификаторы уже заняты, сохранить обратную совместимость протокола и документировать согласованную схему.

Не заменять существующий заголовок упрощённым пятибайтовым заголовком из учебного примера.

Защитить весь необходимый игровой обмен, включая:

- MOVEMENT;
- SHOOT;
- STATE_UPDATE и репликацию;
- ACK и механизмы надёжной доставки;
- PING/PONG и другие сообщения игровой сессии.

Исключение — необходимые сообщения установления защищённой сессии.

### Отправка

Сериализация существующего сообщения → формирование окончательного заголовка → AES-GCM → UDP.

### Получение

UDP → проверка минимальной структуры и размера → поиск сессии → проверка replay → AES-GCM authentication/decryption → десериализация → существующий обработчик игровой логики.

Не допускать обработки plaintext игровых пакетов в режиме, где шифрование обязательно.

### Совместимость с предыдущими работами

Сохранить:

- надёжную доставку SHOOT;
- ненадёжную передачу MOVEMENT;
- ACK, RTO и retransmission;
- дедупликацию команд;
- prediction/reconciliation;
- интерполяцию и синхронизацию;
- оптимизацию сетевого трафика;
- работу нескольких клиентов.

Повторные передачи одного datagram должны корректно обрабатываться совместно с защитой от replay. Валидные повторные передачи не должны приводить к повторному исполнению команды SHOOT.

## 5. Безопасность сессий и защита от атак

Реализовать:

1. Хранение независимого криптографического контекста на каждую сессию.
2. Отдельные счётчики исходящих пакетов по направлениям.
3. Sliding replay window для входящих nonce/counter.
4. Отклонение ранее обработанных пакетов.
5. Корректную обработку перестановки UDP-пакетов.
6. Ограничение числа незавершённых handshake.
7. Rate limiting для попыток установления сессии.
8. Тайм-аут неактивных сессий и освобождение ресурсов.
9. Сброс криптографического состояния при переподключении и смене ключей.
10. Запрет повторного использования ключа с уже применённым nonce после перезапуска или переподключения.

Логировать безопасные события:

- `HANDSHAKE_OK`
- `HANDSHAKE_FAIL`
- `AUTH_FAIL`
- `REPLAY_DROP`
- `RATE_LIMIT`
- `SESSION_EXPIRED`

Не логировать секреты, полные сессионные ключи и открытый игровой plaintext.

### Проверить отдельно дефекты учебного примера

В приложенном клиенте и сервере `payloadSize` изменяется после EncryptAES, хотя заголовок уже использован как AAD. Исправить порядок построения пакета.

Также проверить:

- валидацию ответа KEY_EXCHANGE;
- проверку адреса отправителя;
- отсутствие replay protection;
- обработку некорректных длин;
- разделение ключей для направлений;
- корректность выхода тестов с ненулевым кодом при ошибке;
- поддержку DNS-имени сервера;
- отсутствие неограниченного роста таблицы сессий.

## 8. Тестирование

### Криптография

- X25519: стороны получают одинаковый общий секрет.
- HKDF: корректный вывод ключей.
- AES-GCM: успешный encrypt/decrypt.
- Подмена ciphertext отклоняется.
- Подмена AAD отклоняется.
- Подмена tag отклоняется.
- Подмена nonce отклоняется либо приводит к безопасному отклонению при отсутствии валидной аутентификации.

### Протокол

- Успешный handshake.
- Тайм-аут handshake.
- Повторный handshake.
- Несколько независимых сессий.
- Повтор старого пакета.
- Пакеты не по порядку в допустимом replay window.
- Пакеты вне replay window.
- Неправильный payloadSize.
- Изменение любого аутентифицируемого поля Header.
- Превышение допустимого размера пакета.

- Повтор SHOOT не приводит к повторному выстрелу.

- RTT/jitter/loss продолжают измеряться.
- Prediction и reconciliation не нарушены.
- Синхронизация нескольких игроков работает.
- Оптимизация трафика ПР №5 сохранена.

Повторить основные измерения сетевой нагрузки предыдущей практической работы и отдельно показать накладные расходы шифрования в байтах и процентах.

## 11. Критерии приёмки

**ПР №6 можно считать программно завершённой, если:**

- Шифрование реализовано непосредственно в действующем UDP-протоколе.
- Клиент и сервер реально согласовывают сессионные ключи.
- Игровая полезная нагрузка передаётся через AES-256-GCM.
- Некорректные authentication tag и AAD приводят к отклонению пакетов.
- Повторные пакеты не исполняются повторно.
- Работают несколько независимых клиентов.
- Предыдущие практические работы не сломаны.
- Все доступные unit и integration tests пройдены.
- Есть реальное подтверждение работы клиент-серверного обмена.
- Документация обновлена.

**Полное соответствие методичке**, включая Cloudflare Spectrum и скриншоты панели, подтверждать только после реальной внешней настройки и тестирования.

3. Список изменённых файлов и краткое назначение каждого изменения.
4. Описание архитектуры шифрования и интеграции.
5. Все фактически выполненные команды сборки и тестов.
6. Реальные результаты тестов, число PASS/FAIL.
7. Результаты клиент-серверного тестирования.
8. Сравнение сетевого трафика с ПР №5.
9. Расположение документации и доказательств.
10. Оставшиеся технические и инфраструктурные ограничения.
11. Git diff summary и готовность к Pull Request.

Использовать четыре объективных вердикта для итоговой оценки: «Подтверждено», «Опровергнуто», «Частично подтверждено», «Недостаточно данных».

**Не ограничивайся аудитом или планом. После изучения репозитория внеси необходимые изменения в код, выполни доступные проверки и предоставь проверяемый результат. Не имитируй выполненные тесты, захват Wireshark, подключение Cloudflare или проверку Unity.**

При недоступности внешней инфраструктуры заверши все независимые от неё программные этапы и документируй блокирующие факторы отдельно.
