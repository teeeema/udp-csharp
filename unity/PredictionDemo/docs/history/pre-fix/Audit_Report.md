## C. Архитектура и репликация

На Host в устойчивом первом соединении **52 NetworkObject: 50 props + 2 игрока**. При позднем втором Client — 53, при ожидании timeout убитого клиента кратковременно 54; это включает ещё не удалённого отключённого игрока. Отдельный runtime spawn доводил props до 51. В optimized клиент закономерно получает меньше 50 props.

Состав: Kind 0 — 20 статичных ящиков; Kind 1 — 15 мишеней с серверной синусоидальной траекторией; Kind 2 — 10 индикаторов Phase; Kind 3 — 5 pickups. Position, Kind, Health, Phase и OptimizedMode — серверные NetworkVariable. Клиент не получает право записи в них. Надёжный owner-only FireRpc и owner-only SubmitInputRpc защищают чужое владение на уровне NGO. Однако движение не ограничено серверным временем (H01), поэтому безопасная авторитетность подтверждена лишь частично.

BASELINE действительно не использует дистанционную фильтрацию, periodic snapshots затрагивают все 50 объектов, и статичные props не спят. NGO dirty tracking действует штатно в обоих режимах. Полные снимки дублируют NetworkVariable, а hp/phase в SnapshotRpc не используются. Большая базовая нагрузка реализована намеренно, что видно в старом отчёте, но её нельзя выдавать за нагрузку обычного NGO-проекта без специальных излишеств.

OPTIMIZED: расстояние сравнивается по squared distance с радиусом 38 м, наблюдатели выбираются отдельно по ClientId, NetworkHide/Show выполняются раз в 0,2 с. На движущемся клиенте число props увеличивалось с 10–11 до 21 по мере приближения. Проверены authoritative relocation вне/в радиус и повторное получение состояния объекта после скрытия; это не равно полному тесту пешего выхода/возврата. Два удалённых клиента были одновременно подключены; глубоко разнесённые зоны с независимо проверенным ожидаемым набором каждого клиента не покрыты полностью.

Частота: глобальные счётчики Updates в .state подтверждают уменьшение числа вызовов snapshot; baseline обычно около 1400–1500 вызовов/с для 50 props, optimized примерно 80–110 для 15 мишеней и 10 индикаторов. Это серверные вызовы, а не число датаграмм или клиентских deliveries. Target 30/5/2 Hz ограничен Update и кадровой нагрузкой. Диагностический idle интервал retake содержал подключение Client только в части окна, поэтому его нельзя использовать как честное парное idle-сравнение; для него используются отдельные чистые запуски исходной .app.

«Сон» — прекращение периодического RPC/Phase для статичных Kind 0/3; изменения Health продолжают передаваться штатными надёжными NetworkVariable. Серверное изменение статичного HP до 70 получено клиентом. Это функциональная политика, не API Net Dormancy. Снижение частоты и «сон» — два режима одного scheduler gate, а не независимые реализации двух полноценных движковых технологий. При этом **relevance + cadence уже дают две функциональные оптимизации**. Округление до 0,1 м уменьшает число изменений, но Vector3 остаётся float32 и wire-размер не сжимается.

Траектории игроков, CSP и серверная коррекция сохранены. В matrix Client действительно получил коррекцию **33,941 м** после искусственного серверного смещения и следующего ввода, в обоих режимах. В отдельном UTP-loss тесте сервер принял первый dash и отклонил второй по cooldown, локальный отклик залогирован как 0 мс. Ненулевая коррекция под потерями не воспроизвелась: B-dash упёрся в препятствие и предсказанный/серверный конечные положения совпали. Этот тест не засчитан как проверка коррекции под loss.

TX считает переданное API число байт, не подтверждённую передачу сетевым интерфейсом. Повторы UTP, ACK и заголовки не входят. Первая пара исходной сборки: одинаковые process flags, profile 0, порт 7815, прогрев до 8 с, 20 секундных отсчётов 8–28 с, 50 серверных props; игроки действительно подключены. Активная пара исходной .app: движется и стреляет Client, Host неподвижен; client --pr4-auto упирается в коллизии, поэтому это не свободное перемещение по всей карте.

Диагностическая сборка использует неизменённую игровую реализацию плюс локальный observer/driver: Host input подаётся в тот же серверный обработчик строго с фиксированной частотой; Client input — через Unity Input System. Точки/порядок действий одинаковы, но реальные маршруты ограничиваются коллизиями, запуск других диагностик и CPU/render нагрузка менялись. Поэтому её проценты — **ориентировочные профили активных этапов, а не строгий performance benchmark**. Нельзя объединять эти выборки с чистыми .app опытами в одну среднюю или заявлять доверительный интервал по единственному парному прогону.

Входящий поток Client, состав объектов и startup peaks записаны отдельно в evidence/original-build/summary.json и CSV. Startup max — максимум секундных интервалов при подключении, а не чисто выделенный пакет spawn. Spawn всех объектов перед последующим cull увеличивает начальную нагрузку. Агрегация старого скрипта — невзвешенное среднее секундных rates; при почти равных интервалах нормально, при stalls лучше delta(total bytes)/delta(time), именно этот вариант применяется к .state диагностике.

Почему 99,679%: baseline рассылает полное состояние даже неподвижных объектов; при неподвижном наблюдателе почти все реально движущиеся мишени находятся вне радиуса; optimized оставляет в зоне главным образом статичные ящики и служебные NGO updates. Отсутствия всех необходимых обновлений не обнаружено, но это не оправдывает игровой баг урона и нарушения бюджета ввода. Для активной Client-нагрузки чистый повтор дал около 96,39%, а диагностическая одновременная активность — около 94,55%. Переносить 99,679% на любую игру нельзя.
